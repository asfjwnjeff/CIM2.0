# CIM2.0 地址主数据管理 — 业务调研报告

> 日期：2026-06-26
> 目的：梳理当前地址管理现状、痛点与改进方向，作为后续设计与开发的参考基线。

---

## 一、业务背景

CIM2.0 定位为公司的**客户主数据源头系统**。地址主数据是客户主数据的重要组成部分，覆盖客户注册地址、营业地址、开票地址、运输收货地址、仓储作业地址等多种类型。

当前地址数据分散在多个系统的多个表中，缺乏统一管理和治理能力。本次升级的目标是建立统一的地址主数据管理体系，使 CIM 成为地址的"唯一真相源"，下游系统（COS、TMS、WMS、DMS、CPQ）只消费、不维护。

### 涉及的业务角色

| 角色 | 与地址的关系 |
|------|-------------|
| 客服 | 掌握客户地址变化信息，是地址维护的主要责任人 |
| 订单组 | 在 COS 下单时选择地址，当前也承担了部分地址录入工作 |
| 运输团队（TMS） | 使用地址定位、联系人进行运输调度与配送 |
| 仓储团队（WMS） | 使用地址进行出入库作业管理 |
| 关务团队（DMS） | 使用地址的关务属性（监管区域、境内外等） |
| 财务团队 | 使用开票地址进行发票处理 |

## 二、现状：地址数据散落分布

### 2.1 当前地址字段全景

系统中包含地址信息的字段散落在 **5 张表、7+ 个字段**中：

| 存储位置 | 字段 | 地址类型 | 格式 | 是否有解析 | 是否有版本 |
|---------|------|---------|------|-----------|-----------|
| `customers.basicInfo` (JSON) | addressProvince/City/District/Detail | 公司营业地址 | 省/市/区/详细 四段 | ✗ | ✗ |
| `customers.businessInfo` (JSON) | registeredAddress | 注册地址 | 纯文本 | ✗ | ✗ |
| `customers.businessInfo` (JSON) | correspondenceAddress | 通信地址 | 纯文本 | ✗ | ✗ |
| `customers` | invoiceAddress | 开票地址 | 纯文本 | ✗ | ✗ |
| `service_entities` | address | 注册地址 | 纯文本 | ✗ | ✗ |
| `signing_entities` (store) | address | 注册地址 | 纯文本 | ✗ | ✗ |
| `contacts` | address | 联系人地址 | 纯文本 | ✗ | ✗ |
| `address_sites` | 完整结构化字段 | 运输地址 | 省/市/区/详细/经纬度/版本 | ✓ | ✓ |

### 2.2 核心问题

1. **同一物理地址多处存储**：例如上海张江工厂，其注册地址、营业地址、收货地址可能是同一个地点，但在系统中以不同格式存储在 4 个不同位置
2. **大部分是纯文本**：无法地址解析、无法经纬度定位、无法结构化检索
3. **无版本追溯**：除运输地址外，其余地址修改后无历史记录
4. **无编码管理**：除运输地址有 ADS 编码外，其余地址无统一编码
5. **无法全局查询**：要找一个客户的所有地址，需要跨多张表分别查询

## 三、现状：运输地址现有流程

### 3.1 当前数据层级

运输地址是当前唯一有结构化管理的地址类型，其层级为：

```
服务主体 (service_entities)
  └── 收发货方 (shipper_consignees)
       └── 地址站点 (address_sites)
            ├── 地址用途 (address_usages) — 多个
            ├── 地址联系人 (address_contacts) — 多个
            └── 地址版本 (address_versions) — 修改自动快照
```

### 3.2 当前录入流程

```
客服知道客户地址变化
  → 通过邮件/微信通知订单组
  → 订单组在 COS 录入或修改地址
  → COS 保存地址
  → 订单组用新地址下单
```

**痛点**：
- 客服掌握信息但不录入系统，订单组不掌握信息但要录入
- 信息传递靠邮件/微信，易出错、无留痕
- COS 既是地址维护系统又是订单系统，职责混合

### 3.3 当前修改流程

当前在 COS 中直接修改地址字段，修改后立即生效。无版本快照，无法追溯"谁在什么时候改了什么"。

### 3.4 当前停用流程

停用无系统化流程。地址不再使用后可能被直接删除，也可能保留但无标记。已被订单引用的地址删除后会导致历史订单数据不完整。

## 四、现状：地址解析

### 4.1 当前解析能力

CIM 已接入高德地图 Geocoding API，可对国内地址进行结构化解析：

- **输入**：详细地址文本
- **输出**：省、市、区/县、标准化地址、经纬度、精度等级

### 4.2 解析精度边界

高德 API 的解析精度上限为**道路+门牌号级别**（如"张江路 2000 号"）。以下内容**无法被解析**：

| 无法解析的内容 | 示例 |
|-------------|------|
| 产业园区内部编号 | "XX 半导体产业园内" |
| 楼栋/楼层/房间号 | "5 号楼 301 室" |
| 仓库/月台编号 | "3 号仓 B 区" |
| 企业内部建筑物名称 | "研发大楼" |

### 4.3 当前门牌号处理

现有 `address_site` 表已预留 `doorplate` 字段（手工录入），但在当前运输地址录入流程中，门牌号和详细地址的职责划分不够清晰，下游系统接收的地址字段也未明确拼接规则。

## 五、改进：地址分类体系

### 5.1 8 大地址类别

将地址从"运输地址为主"扩展为覆盖全部业务场景的 **8 大类别**：

| 类别 | category 值 | 说明 | 典型归属 |
|------|------------|------|---------|
| 注册地址 | registered | 工商登记地址，法律文书使用 | 客商、签约主体 |
| 营业地址 | business | 实际办公/经营场所 | 客商、主体 |
| 开票地址 | invoice | 发票/结算使用 | 客商、结算主体 |
| 通信地址 | mailing | 邮寄/函件使用 | 客商、联系人 |
| 运输地址 | logistics | 收货/发货/提货/送货/退货/报关 | 服务主体→收发货方 |
| 仓储地址 | warehouse | 仓库/配送中心 | 我司内部、客户仓库 |
| 联系人地址 | contact | 自然人联系地址 | 联系人 |
| 银行地址 | bank | 开户行物理地址 | 结算主体 |

### 5.2 16 个用途标签

| 用途标签 | usage_type | 适用类别 |
|---------|-----------|---------|
| 注册地址用途 | registered | 注册地址 |
| 营业/办公用途 | business | 营业地址 |
| 开票用途 | invoice | 开票地址 |
| 通信/邮寄用途 | mailing | 通信地址 |
| 收货用途 | receiving | 运输地址 |
| 发货用途 | shipping | 运输地址 |
| 提货用途 | pickup | 运输地址 |
| 送货用途 | delivery | 运输地址 |
| 退货用途 | return | 运输地址 |
| 报关用途 | customs | 运输地址 |
| 仓储作业用途 | warehousing | 仓储地址 |
| 联系人地址用途 | contact_addr | 联系人地址 |
| 银行地址用途 | bank_addr | 银行地址 |
| 总部地址用途 | headquarters | 营业地址 |
| 分支机构用途 | branch | 营业地址 |
| 其他用途 | other | 通用 |

### 5.3 类别 vs 用途的关系

- **address_category**（类别）：一条地址只有一个类别，决定该地址的基本属性
- **address_usage**（用途标签）：一条地址可以有多个用途标签，决定该地址出现在哪些业务场景

例如：上海张江工厂 → category = logistics → usages = [receiving, shipping, customs]

## 六、改进：标签化统一管理

### 6.1 核心模型

一张 `address_site` 表管理全部地址。通过 `owner_type` + `owner_id` 关联任意业务对象，通过 `address_category` 区分类别，通过 `address_usage` 标签表达多用途。

```
address_site（统一地址主数据表）
  ├── owner_type + owner_id → 归属任意业务对象
  ├── address_category     → 8 种类型之一
  ├── address_usage (N:M)  → 16 种用途标签
  ├── 地理字段             → 省/市/区/详细/经纬度/解析精度
  ├── address_contact      → 现场联系人（多条）
  └── address_version      → 版本快照
```

### 6.2 归属模型

| owner_type | 说明 | 示例 |
|-----------|------|------|
| customer | 客商 | 应用材料（中国）的注册地址 |
| service_entity | 服务主体 | 服务主体关联的运输地址 |
| signing_entity | 签约主体 | 签约主体的注册地址 |
| settlement_entity | 结算主体 | 结算主体的银行地址 |
| contact | 联系人 | 自然人的联系地址 |
| internal | 我司内部 | 我司仓库、办公室 |

### 6.3 标签化运作方式

同一物理地址可以挂多个用途标签，从而在不同业务视角中同时出现：

```
上海张江工厂 (ADDR-001, category=logistics)
  标签: [registered, business, receiving, invoice]

  客商档案视角（筛选 registered + business）     → 可见
  运输管理视角（筛选 receiving）                → 可见
  财务结算视角（筛选 invoice）                  → 可见
```

修改地址只需改 ADDR-001 一条记录，所有引用它的业务视角自动看到最新值。

## 七、改进：地址组装模型

### 7.1 两层模型

```
用户输入完整地址
      │
      ├── 高德 API 解析 → detail_address（道路级，不可手改）
      │                   例如："上海市浦东新区张江路2000号"
      │
      └── 人工录入 → doorplate（楼栋/房间，可独立修改）
                      例如："5号楼301室"

完整地址 = detail_address + doorplate
        = "上海市浦东新区张江路2000号5号楼301室"
```

### 7.2 变更规则

| 变更场景 | 触发动作 |
|---------|---------|
| 仅修改 doorplate（301→302） | 不触发重新解析，不生成版本快照，仅更新拼接结果 |
| 修改 detail_address（道路级变更） | 触发高德重新解析 → 回填省市区/经纬度 → 生成新版本快照 |
| 同时修改两者 | 先解析后拼接，生成新版本快照 |

### 7.3 下游同步

下游系统接收到的是**完整拼接地址**（detail_address + doorplate），不感知"哪部分是解析的、哪部分是手工录入的"。

## 八、现状→改进：地址新增流程

### 8.1 当前流程

```
客户告知客服地址变化
  → 客服通过邮件/微信通知订单组
  → 订单组在 COS 中找到对应客户
  → 订单组在 COS 中新增/修改地址
  → 订单组下单时使用新地址
```

痛点：客服掌握信息但无权录入、订单组被动录入、信息传递靠线下

### 8.2 目标流程

```
客服在 CIM 中进入对应客商/服务主体
  → 点击「新增地址」
  → 选择归属类型、地址类别
  → 输入详细地址 → 系统自动调用高德解析
  → 解析结果回填省/市/区/经纬度（不可手改）
  → 手工录入门牌号
  → 勾选地址用途标签（多选）
  → 添加现场联系人（可选）
  → 保存 → 系统自动生成 ADDR 编码
  → 地址生效 → 自动同步到 COS/TMS/WMS/DMS
  → 订单组在 COS 下单时可直接选择该地址
```

## 九、现状→改进：地址修改流程

### 9.1 当前流程

在 COS 中直接修改地址字段，无版本记录，修改即生效。谁改的、什么时候改的、改了什么——事后无法追溯。

### 9.2 目标流程

**修正类修改**（联系人、电话、门牌号等小字段）：
- 在 CIM 中直接修改 → 保存 → 不生成新版本 → 下游同步更新

**实质地址变更**（省市区、详细地址、经纬度变化）：
- 在 CIM 中修改 → 触发重新解析（如涉及）→ 保存
- 系统自动 diff 生成 change_summary（如"详细地址: 张江路1688号→张江路2000号"）
- 自动生成新版本快照（address_versions 新增一条记录）
- 版本号 +1
- 下游同步更新

### 9.3 历史订单保护

- COS 下单时保存**地址快照**（订单创建时的地址内容）
- CIM 地址后续修改**不自动覆盖**已完成订单的快照
- 历史订单始终可追溯到下单时的准确地址

## 十、现状→改进：地址停用流程

### 10.1 当前流程

无系统化停用流程。不再使用的地址可能被直接删除，导致历史订单引用断裂。

### 10.2 目标流程

```
客服在 CIM 中选择地址 → 点击「停用」
  → 系统检查是否存在未完成订单引用该地址
    ├─ 有未完成订单 → 提示客服处理（指定替代地址或等待订单完成）
    └─ 无未完成订单 → 确认停用
  → 填写停用原因（必填）
  → status → inactive
  → 同步停用状态到 COS/TMS/WMS/DMS
  → COS 下单时该地址不再可选
  → 历史订单保留当时地址快照
```

**规则**：
- 地址不物理删除，只标记停用
- 已被订单引用的地址不允许物理删除
- 停用原因必须填写

## 十一、改进：现场纠偏反馈闭环

### 11.1 业务痛点（当前无此机制）

当前存在高频但无系统留痕的场景：

```
客户给客服的订单写地址 A
  → 客服告诉订单组在 COS 录入 A
  → COS 推送 TMS
  → TMS 司机送到 A，发现实际是附近的 B
  → 司机自己送到 B
  → 系统中还是 A
  → 下次还用 A → 循环出错
```

痛点：司机发现偏差但无上报渠道、客服不知道地址有误、系统永远记录错误的地址 A

### 11.2 纠偏机制设计

**核心思路**：给地址加一个"核实状态"，建立从现场到源头的反馈闭环。

#### 核实状态流转

```
unverified（未核实，新建默认）
  → 首次成功送达无偏差 → verified（已核实）
  → 现场发现偏差 → 上报纠偏 → discrepancy_found（有偏差）
     → 客服接受修正 → corrected（已修正）
     → 客服拒绝 → 保持原状
```

#### 纠偏表结构

`address_corrections` 记录每次现场反馈：

| 字段 | 说明 |
|------|------|
| reported_address | 现场实际地址 |
| reported_gps_lng/lat | 现场 GPS 坐标 |
| reported_by | 上报人（司机/仓管） |
| reported_by_system | 上报来源（TMS/WMS/COS） |
| discrepancy_detail | 偏差描述 |
| status | pending → accepted → rejected |
| reviewed_by | 审核人（客服） |
| action_taken | update_address / create_new / ignore |

#### 纠偏完整流程

```
TMS 司机发现地址偏差
  → 在 TMS/移动端上报: 实际地址 + GPS + 备注
  → 数据回传 CIM
  → CIM 生成 address_corrections 记录
  → address_site.verification_status → discrepancy_found
  → 通知客服（待办/消息提醒）
  → 客服核实
    ├─ 接受: 更新原地址 → 生成新版本（change_summary 标注"现场纠偏"）
    │   → verification_status → corrected → 下游自动同步修正地址
    └─ 拒绝: 记录审核意见 → 保持原状
```

## 十二、改进：业务场景-地址匹配

### 12.1 匹配逻辑

不同业务操作需要的地址标签不同，系统根据标签自动筛选可用地址：

| 业务操作 | 需要的标签 | 说明 |
|---------|-----------|------|

| 寄送合同函件 | mailing（通信） | 法务选择通信地址 |

| 苏州昆山加工厂 | 收货+发货+报关 | ✓ | | ✓ | ✓ | | |

## 十三、改进：系统间数据流

### 13.1 总体架构

```
CIM（地址唯一源头）
  │
  ├── 实时同步 → COS（订单引用地址）
  ├── 实时同步 → TMS（运输使用定位/联系人）
  ├── 实时同步 → WMS（仓储使用作业地址）
  ├── 实时同步 → DMS（关务使用监管属性）
  └── 实时同步 → CPQ（报价计费引用客户与主体）

数据中台 → 仅订阅分析，不参与业务主链路
```

### 13.2 系统职责边界

| 系统 | 职责 | 不承担的职责 |
|------|------|------------|
| CIM | 地址主数据源头：新增、修改、停用、编码、解析、版本、纠偏 | 不承担订单履约、运输调度、仓储作业 |
| COS | 下单时引用 CIM 已生效地址，保留订单地址快照 | 不再作为地址维护入口 |
| TMS | 使用地址定位、联系人、运输要求进行配送 | 不维护地址源头 |
| WMS | 使用仓储作业地址、预约要求 | 不维护地址源头 |
| DMS | 使用监管区域、境内外主体、关务属性 | 不维护地址源头 |
| CPQ | 使用客户、签约主体、结算主体信息 | 不主导客户档案治理 |
| 数据中台 | 数据分析、报表、质量监控 | 不参与业务主链路、不反向修改 CIM |

### 13.3 同步策略

| 操作 | 同步动作 |
|------|---------|
| 新增地址 | 同步新增到下游 |
| 修改地址 | 同步变更 + 版本号 |
| 停用地址 | 同步停用状态 |
| 删除地址 | 原则上不物理删除，只同步停用 |
| 同步失败 | CIM 显示失败状态 + 支持手动重试 |
| 下游反向修改 | **禁止**，下游系统不可反向修改 CIM 主数据 |

---

## 十四、改进：编码规则

### 14.1 统一编码格式

| 编码前缀 | 对象 | 格式 | 示例 |
|---------|------|------|------|
| SVC | 服务主体 | SVC-YYYYMMDD-NNN | SVC-20260626-001 |
| SHC | 收发货方 | SHC-YYYYMMDD-NNN | SHC-20260626-001 |
| ADDR | 地址站点（统一） | ADDR-YYYYMMDD-NNN | ADDR-20260626-001 |
| CORR | 纠偏记录 | CORR-YYYYMMDD-NNN | CORR-20260626-001 |

### 14.2 编码规则

- 基于 `code_sequences` 表原子递增
- 跨日自动重置序号（从 001 重新开始）
- 旧 ADS 编码保留在 code 字段，不做强制迁移
- COS 旧代码保留为历史映射字段，不作为 CIM 主键

---

## 十五、改进：地址复制/复用

### 15.1 设计原则

- 地址不设为全公司公共地址池
- 不同客户的地址默认隔离，保护商业隐私
- 即使文字地址相同，业务关系、联系人、用途也可能不同

### 15.2 复制机制

当确实需要跨客户复用地址时，使用"复制地址"功能：

```
客服在客商 A 下选中一个地址 → 点击「复制到其他客商」
  → 选择目标客商/主体
  → 确认归属关系
  → 系统生成新的 ADDR 编码
  → 复制后的地址归属于新客商
  → 后续独立维护，与原地址无自动联动
```

- 复制后的地址与原地址**没有自动联动关系**
- 各自独立修改、停用
- 不会因为原地址变更而自动更新复制地址

## 十六、其他说明

### 16.1 联系人变更 vs 地址变更

- 地址联系人（address_contacts）修改 → **不影响**地址版本
- 地址本身（detail_address、doorplate 等）修改 → 触发版本快照（如涉及道路级变更）
- 两者独立管理，互不影响

### 16.2 在途货物地址变更

- 当前做法：货物在途后地址不做系统修改，通过电话/微信线下通知司机
- 新方案：不在系统中做在途地址变更，保持当前线下处理方式

### 16.3 待定事项

以下事项待后续讨论确认：

| 事项 | 当前状态 |

| 地址去重与合并规则 | 待定 |
| 权限模型（各角色对地址的查看/新增/修改/停用权限） | 待定 |
| 地址审批流程（新增/修改/停用是否需要审批） | 当前不启用审批，系统预留审批开关 |
| 境外地址纳入首期范围 | 模型支持，首期按实际业务范围决定 |

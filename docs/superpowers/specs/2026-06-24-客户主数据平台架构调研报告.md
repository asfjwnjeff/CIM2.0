# CIM2.0 客户主数据平台架构调研报告

> 调研日期：2026-06-24  
> 调研目的：为 CIM2.0 从业务工具升级为"客户主数据中心"平台提供架构参考

---

## 1. 核心发现：业界主流架构模式

### 1.1 两大架构模式对比

| | 方案 A：统一 Party 模型 | 方案 B：独立分域模型 |
|---|---|---|
| **代表** | SAP Business Partner、金蝶 AMDM | 用友 MDM、中远海运 |
| **思路** | 法律实体为唯一锚点，角色为扩展标签 | 客户域和供应商域各自独立建模 |
| **适用** | 客商重叠度高、集团型/多业态 | 客商角色清晰、业务交集小 |
| **优势** | 360度统一视图、避免数据冗余 | 各自独立治理、角色专属属性清晰 |
| **劣势** | 治理流程复杂、需处理多态性 | 同一实体重复录入、无法形成统一视图 |

### 1.2 SAP Business Partner 模型（业界金标准）

SAP S/4HANA 的核心设计：

```
                    Business Partner (BP) —— 唯一主导对象
                    - BP 编号（全局唯一 GUID）
                    - 法定名称 / 地址 / 税号 / 银行（共享属性）
                           /              \
                    Customer Role        Vendor Role
                    (FLCU00/FLCU01)      (FLVN00/FLVN01)
                    - 信用额度            - 付款条件
                    - 销售区域            - 采购组织
```

**核心原则**：
- **一个法律实体 = 一条 BP 记录**，不可重复建档
- **角色是多选的**：同一 BP 可同时是 Customer + Vendor
- **CVI（Customer-Vendor Integration）**：BP 变更实时同步到下游业务表
- **旧表（KNA1/LFA1）不删除但不可直接维护**——这是兼容层而非源头

**为什么 SAP 从分离模型转向统一 BP 模型**：
1. 数据冗余：同一公司在 KNA1 和 LFA1 中分别维护两套完全独立的记录
2. 维护成本高：地址变更、银行账户更新必须在两个地方重复操作
3. 无 360 视图：无法看到同一公司的完整应收+应付关系
4. 统一维护入口后效率提升约 40%，供应商入驻时间缩短 70%

### 1.3 国内平台实践

**金蝶 AMDM（客商统一模型）**：
- 客户和供应商纳入统一的"客商主数据"管理域
- 集团总部定义公共属性标准，下级单位扩展个性化字段
- 通过相似度算法识别疑似重复客商
- 菜单结构：数据建模 → 主数据维护（客商/物料/人员/组织/财务）→ 参考数据维护 → 主数据集成 → 流程管理 → 监控告警

**用友 MDM（分域模型）**：
- 客户属于"客商域"（外部组织），主体属于"主体域"（内部组织）
- 主体域分两个架构：管理架构（HR 来源）和财务法人架构（财务来源）
- 覆盖 6 大类主数据域：客户域、主体域、人员域、产品域、项目域、财务域

**中远海运集团**：
- 9 大主数据域：客户、供应商、会计科目、银行代码、贷款人、船舶、货种、港口、燃油
- 客户/供应商分域独立管理，各有独立管理细则
- 技术栈：SAP Portal + BPM + MDM + PI（数据分发）

**某世界领先物流集团**（半导体供应链相关）：
- 采用"外部单位"统一模型：以法律实体为统一入口
- 通过"业务角色"标签区分：客户 / 供应商 / 既是客户又是供应商
- 引用工商数据（天眼查/企查查）作为基准校验

## 2. DAMA 数据管理体系参考

### 2.1 主数据管理边界

DAMA-DMBOK 定义的主数据管理核心原则：

1. **"一数一源一标准"** — 每个客户主数据属性只能有一个权威源头系统
2. **唯一性识别** — 通过统一社会信用代码等证件组合判定唯一性，建立"黄金记录"
3. **跨系统共享** — 销售、客服、财务系统共享同一份主数据正本

### 2.2 主数据管理的四大体系

| 体系 | 内容 |
|------|------|
| 标准体系 | 数据编码规则、属性规范 |
| 管控体系 | 组织、流程、评估与考核、系统 |
| 质量体系 | 合理性、真实性、完整性、唯一性、及时性 |
| 安全体系 | 分级、授权 |

### 2.3 理想架构

```
[主数据唯一正本 CIM] → 同步 → [COS/CPQ/TMS/WMS/DMS 各业务系统]
```

现实演进路径：
```
Step 1: 各业务系统 → 汇聚到 CIM Hub → 清洗治理 → 分发回业务系统
Step 2: CIM 成为唯一维护入口 → 业务系统只消费
```

## 3. MDM 平台导航设计最佳实践

### 3.1 推荐一级导航结构

基于 SAP MDG Fiori、金蝶 AMDM、Stibo STEP 等平台的综合分析：

| 一级导航 | 二级内容 | 说明 |
|----------|---------|------|
| **工作台** | 仪表盘、我的待办、数据概览 | 角色化首页 |
| **主数据管理** | 客户/供应商/物料/组织等按域划分 | 核心操作区 |
| **数据查询** | 全局搜索、高级检索、数据浏览 | 只读消费入口 |
| **数据治理** | 审批工作台、质量监控、匹配去重、变更日志 | 治理管控 |
| **数据架构** | 数据模型、编码规则、层级配置、分发管理 | 元数据管理 |
| **系统配置** | 用户管理、角色权限、流程配置 | 平台管理 |

### 3.2 导航设计原则

- **三级深度上限**：一级领域 → 二级实体 → 三级操作/视图
- **一级菜单 4-6 个**，二级菜单 ≤6 个
- **左侧垂直手风琴式**，支持角色化显示/隐藏
- **全局搜索作为核心导航入口**，支持跨实体模糊搜索
- **不同角色看到不同菜单**，无权限项直接不渲染（非置灰）
- **避免反模式**：级联飞出菜单、Tab+下拉混合、过多顶级菜单

### 3.3 B2B 场景下"法律实体"与"业务角色"的导航处理

核心原则：**同一 BP 不同角色用 Tab 切换，跨法律实体跳转用面包屑，层级浏览用侧边栏树**

```
详情页结构：
┌─────────────────────────────────────────────┐
│ 面包屑：主数据管理 > 客户 > 华为技术有限公司    │
├─────────────────────────────────────────────┤
│ [基本信息] [客户视图] [供应商视图] [层级关系]   │  ← Tab 切换角色
├─────────────────────────────────────────────┤
│                                              │
│  法律实体信息：                                │
│  名称 / 统一社会信用代码 / LEI / 注册地址      │
│                                              │
│  业务角色标签：                                │
│  [签约主体] [服务主体] [结算主体]               │  ← 角色标签
│                                              │
│  地址与收发货方：                              │
│  └── 服务主体 A                               │
│      ├── 收发货方 1                           │
│      │   ├── 地址站点 ①（收货/发货）            │
│      │   └── 地址站点 ②（仓储）                │
│      └── 收发货方 2                           │
└─────────────────────────────────────────────┘
```

## 4. 对 CIM2.0 的架构建议

### 4.1 现状分析

当前 CIM2.0 存在"客户管理"和"主体管理"两个独立菜单，但底层管理的是同一批法律实体（通过角色标签区分签约/服务/结算），这是 SAP 从 KNA1/LFA1 升级到 BP 之前同样的历史遗留模式。

**核心问题**：用户（客服）不明白"客户"和"主体"有什么区别，因为在实际业务中没有区别——一个法律实体就是他们操作的全部。

### 4.2 方案建议

以下提供三个方案供选择：

---

#### 方案 A：统一入口 + 角色标签（推荐）

**对标**：SAP Business Partner 模型、金蝶"客商主数据"统一模型

**核心理念**：一个法律实体 = 一条主数据记录 = 一个详情页入口。角色标签（签约/服务/结算）只是这条记录上的属性。

**菜单结构**：
```
工作台
主数据管理
  ├── 主体档案        ← 合并原"客户管理"+"主体管理"
  ├── 地址主数据       ← 独立一级，跨服务主体视角
  └── 联系人管理
业务管理（原有）
  ├── 客户跟进
  ├── 商机管理
  ├── 售前报价
  └── 风控审批
结算管理（原有）
  ├── 账单主体规则管理
  └── 账单拆分字段管理
系统管理（原有）
```

**主体详情页内部 Tab**：
```
[基本信息] [业务档案] [角色与绑定] [收发货与地址] [联系人] [财务与风控]
```

**导航路径**：`主数据管理 → 主体档案 → 点击名称 → 详情页（含所有子模块）`

**优点**：
- 用户不需要理解"客户 vs 主体"的区别
- 一个入口找到所有信息，不需要跨模块跳转
- 与 SAP BP 模型对齐，未来扩展到供应商管理只需加角色标签
- 地址主数据独立菜单，支持跨主体的全局检索和治理

**缺点**：
- 需要合并现有"客户管理"和"主体管理"的字段和数据
- 改动较大

---

#### 方案 B：保留双入口 + 明确分工

**对标**：用友 MDM 模型

**核心理念**："主体管理"管法律实体档案，"客户管理"管业务关系，两者通过统一社会信用代码关联。

**菜单结构**：
```
工作台
客户管理        ← 聚焦业务关系：等级、行业、跟进、服务产品
主体管理        ← 聚焦法律档案：信用代码、法人、注册信息
  ├── 服务主体   ← 下挂地址主数据
  ├── 签约主体
  └── 结算主体
地址主数据      ← 独立一级，全局地址视图
业务管理...
```

**优点**：
- 改动较小，现有模块基本保留
- 业务人员（客服）和基础数据管理员各用各的入口

**缺点**：
- 同一法律实体在两个菜单都出现，用户仍然困惑
- 业务属性和法律属性实际难以清晰分界
- 与你的文档中"CIM 成为客户主数据源头"的方向不够一致

---

#### 方案 C：按业务域划分（中远海运模式）

**对标**：中远海运集团 9 大主数据域

**核心理念**：按业务域（客户域、供应商域、地址域、合同域等）各自独立管理，各自有独立编码体系。

**优点**：
- 各域边界清晰，治理独立
- 适合集团多业态、各业务线独立运作

**缺点**：
- 可能出现同一实体多域重复录入
- 需要后期做跨域去重和关联
- 组织成本较高

---

### 4.3 我的推荐：方案 A

理由：
1. **你的文档已经指明了方向**：CIM 要做"客户主数据源头系统"，统一入口是平台化的必然选择
2. **半导体供应链行业**客商重叠度通常很高——同一个法律实体往往既是客户又是供应商（如果未来扩展供应商管理的话）
3. **SAP 已经证明了这条路**：从 ECC（KNA1/LFA1 分离）到 S/4HANA（BP 统一），全行业都在走统一 Party 模型
4. **减少用户认知负担**：客服不需要区分"我要去客户管理还是主体管理"

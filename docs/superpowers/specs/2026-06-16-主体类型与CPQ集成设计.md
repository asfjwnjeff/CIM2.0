# 主体类型标记与 CPQ 集成设计

**日期**: 2026-06-16  
**状态**: 待实施  
**版本**: v1.0

## 一、背景与目标

### 1.1 当前问题

- CIM 新建客户 = 签约主体，这是系统目前唯一的主体类型认知
- 签约主体走完风控审批后推送 CPQ，CPQ 中会产生服务主体、结算主体及其多对多绑定关系
- CPQ 回推主体数据到 CIM 时仅含核心字段（名称、信用代码等），大部分信息为空
- 用户需要在 CIM 中识别公司的主体类型、查看绑定关系，并对服务主体进行信息补全

### 1.2 目标

用**最小必要改动**，在客户管理模块实现：

1. 客户列表中能区分签约/服务/结算主体，并能按类型分组筛选
2. 清晰展示主体之间的绑定关系（多对多），支持点击跳转
3. CPQ 推送的服务/结算主体有信息完整度提示，引导用户补全必填字段
4. 签约主体 = 服务主体时（同一信用代码），合并为一条记录显示双标签

### 1.3 不改动范围

- `/entities/` 主体管理页面保持占位
- 客户新增页仅用于创建签约主体（流程不变）
- CPQ 推送 API 接口后做，本次纯前端
- 移动端不涉及

## 二、数据模型

### 2.1 Customer 类型新增字段

```typescript
// ====== 主体标记 ======

/** 主体类型标签（CPQ 回传后确定，可多选，如同时是签约+服务主体） */
entityTypes?: EntityType[];

/** 数据来源系统 */
sourceSystem?: 'cim' | 'cpq';

/**
 * 绑定关系（一对多）
 * 当公司同时是签约和服务主体时，不包含自身的引用
 */
boundCustomers?: BoundCustomer[];

/** 主体类型枚举 */
type EntityType = 'signing' | 'service' | 'settlement';

interface BoundCustomer {
  customerId: string;
  customerName: string;
  entityType: EntityType;
  unifiedSocialCreditCode?: string; // 用于判断同一家公司
}

// ====== CPQ 专属字段（仅 sourceSystem='cpq' + 服务/结算主体时在 UI 显示） ======

/** 境内外标志 */
domesticFlag?: 'domestic' | 'overseas';

/** 结算周期 */
settlementCycle?: string;

/** 开票地址 */
invoiceAddress?: string;

/** 银行结算信息（多组） */
bankAccounts?: BankAccount[];

interface BankAccount {
  currency: string;       // 币种
  bankName: string;       // 开户行
  accountNumber: string;  // 银行账号
}

/** 关联类型（仅结算主体） */
settlementRelationType?: 'service_entity' | 'supplier';

/** 关联名称（仅结算主体） */
settlementRelationName?: string;
```

### 2.2 同一个公司的判断

通过 `unifiedSocialCreditCode` 匹配。签约主体和服务主体信用代码相同 → 合并为一条 Customer 记录，`entityTypes` 含两个标签。

## 三、信息完整度

### 3.1 计算规则

只统计**必填字段**的填写率，非必填字段不参与计算：

```
完整度 = 已填的必填字段数 / 该主体类型的总必填字段数 × 100%
```

### 3.2 各主体类型必填字段清单

**签约主体（CIM 来源）**：
name, responsiblePersons, unifiedSocialCreditCode, industryCategory, countryRegion, serviceProducts

**服务主体（CPQ 来源）**：
上述签约主体必填项 + domesticFlag + settlementCycle + invoiceAddress + ≥1 组 bankAccounts

**结算主体（CPQ 来源）**：
上述签约主体必填项 + domesticFlag + settlementCycle + invoiceAddress + ≥1 组 bankAccounts + settlementRelationType + settlementRelationName

### 3.3 触发条件

仅以下两种状态计算并显示完整度：
- `status === 'draft'`（草稿）
- `sourceSystem === 'cpq'` 且 `entityTypes` 包含 `'service'` 或 `'settlement'`（CPQ 推送的主体）

## 四、UI 设计

### 4.1 客户列表页

| 改动项 | 位置 | 说明 |
|--------|------|------|
| **主体类型分组 pill** | 搜索栏下方、表格上方 | `全部主体` \| `签约主体` \| `服务主体` \| `结算主体`，选中品牌色填充，按 `entityTypes` 筛选 |
| **主体类型标签列** | 表格/卡片 | 蓝色(签约) / 绿色(服务) / 橙色(结算)，可多个标签同时显示 |
| **关联主体数量列** | 表格/卡片 | `签约×2 服务×1` 格式，点击数量弹出关联列表浮窗，0 的不显示 |
| **不完整提醒** | 行内 | ⚠️ 图标（hover tooltip 显示完整度百分比）+ 浅橙色行背景高亮 |
| **信息完整度 badge** | 行内 | 仅草稿 + CPQ 服务/结算主体显示进度百分比 |

### 4.2 客户详情页

| 改动项 | 位置 | 说明 |
|--------|------|------|
| **信息补全横幅** | 页面顶部，Tab 上方 | 条件显示；黄色 warning 底色 + ⚠️ 图标 + 完整度百分比 + [去补全信息 →] 按钮 |
| **主体类型标签** | 基本信息卡片顶部 | 彩色标签，同列表 |
| **绑定关系区** | 基本信息卡片内，主体标签下方 | 列表展示 `主体类型 — 公司名称 →`，点击跳转到对应客户详情 |

### 4.3 补全横幅触发条件

同时满足三个条件时显示：
1. `sourceSystem === 'cpq'`
2. `entityTypes` 包含 `'service'` 或 `'settlement'`
3. 必填字段完整度 < 100%

完整度达标后自动隐藏。

### 4.4 条件渲染规则

```
CPQ 服务主体专属字段（结算周期、银行信息等）
  → 仅 entityTypes 含 'service' 且 sourceSystem='cpq' 时，在详情/编辑页显示

CPQ 结算主体专属字段（开票地址、关联类型、关联名称、银行信息等）
  → 仅 entityTypes 含 'settlement' 且 sourceSystem='cpq' 时，在详情/编辑页显示

上述字段在签约主体（sourceSystem='cim'）的详情/编辑页完全不出现
```

## 七、验证要点

1. **分组筛选**：点选主体类型 pill，列表正确过滤
2. **双标签**：签约=服务主体的记录显示两个类型标签
3. **关联数量**：点击数量弹出浮窗，列出具体关联主体，点击可跳转
4. **补全横幅**：CPQ 服务主体进入详情 → 显示横幅 → 点"去补全" → 进入编辑页 → 填写必填字段 → 横幅消失
5. **条件渲染**：签约主体详情页不出现 CPQ 专属字段；服务/结算主体详情页出现
6. **⚠️ 提醒**：列表行完整度 < 100% → ⚠️ 图标 + 浅橙色行背景
7. **深色模式**：所有新增 UI 在暗色模式下颜色正常

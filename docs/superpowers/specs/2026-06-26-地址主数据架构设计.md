# CIM2.0 地址主数据架构设计

> 日期：2026-06-26
> 背景：当前 `address_site` 表仅服务运输场景（服务主体→收发货方→地址站点），需扩展为全类型地址主数据管理。

---

## 一、现状分析：地址数据散落现状

### 1.1 地址字段分布全景

当前系统中包含地址信息的字段散落在 5 张表、7+ 个 JSON 嵌套字段中：

```
┌─────────────────────────────────────────────────────────────────┐
│                    当前地址字段分布（散、乱、无治理）              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  customers 表                                                    │
│    ├── basicInfo.addressProvince    ← 营业地址-省 (JSON内)       │
│    ├── basicInfo.addressCity        ← 营业地址-市 (JSON内)       │
│    ├── basicInfo.addressDistrict    ← 营业地址-区 (JSON内)       │
│    ├── basicInfo.addressDetail      ← 营业地址-详细 (JSON内)     │
│    ├── businessInfo.registeredAddress  ← 注册地址 (JSON内文本)   │
│    ├── businessInfo.correspondenceAddress ← 通信地址 (JSON内文本)│
│    └── invoiceAddress               ← 开票地址 (独立文本字段)    │
│                                                                 │
│  service_entities 表                                             │
│    └── address                      ← 注册地址 (纯文本)          │
│                                                                 │
│  signing_entities 表 (内存/类型)                                  │
│    └── address                      ← 注册地址 (纯文本)          │
│                                                                 │
│  contacts 表                                                     │
│    └── address                      ← 联系人地址 (纯文本)        │
│                                                                 │
│  address_sites 表 ✓ 唯一结构化管理                                │
│    └── 完整的省/市/区/详细/经纬度/解析/用途/联系人/版本          │
│        └── 但硬绑定 shipperConsigneeId + serviceEntityId NOT NULL│
│            → 只能存运输地址，其他类型塞不进去                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 差距总结

| 维度 | 运输地址 (address_site) | 其他所有地址 |
|------|------------------------|------------|
| 结构化存储 | ✓ 省/市/区/经纬度 | ✗ 纯文本字符串 |
| 地址解析 | ✓ 高德API自动解析 | ✗ 无 |
| 编码管理 | ✓ ADS-YYYYMMDD-NNN | ✗ 无 |
| 版本追溯 | ✓ address_versions 快照 | ✗ 无 |
| 用途标签 | ✓ 7种运输用途 | ✗ 无 |
| 现场联系人 | ✓ address_contacts | ✗ 无 |
| 全局查询 | ✓ /addresses 页面 | ✗ 无法跨类型检索 |
| 重复校验 | ✓ 同收发货方下提醒 | ✗ 无 |

> **结论**：运输地址已经建立了一套完整的治理体系，但其他 7 类地址还停留在"表里一个文本字段"的阶段。升级方向不是另起炉灶，而是把 `address_site` 从「运输专用表」扩展为「统一地址主数据表」。

## 二、地址类型全景

### 2.1 地址分类体系

从业务场景出发，归纳为 **8 大类**：

```
地址主数据分类
├── 1. 注册地址 (registered)         ← 工商登记地址，法律文书使用
├── 2. 营业地址 (business)           ← 实际办公/经营场所
├── 3. 开票地址 (invoice)            ← 发票/结算使用
├── 4. 通信地址 (mailing)            ← 邮寄/函件使用
├── 5. 运输地址 (logistics)          ← 收货/发货/提货/送货/退货/报关
│    └── 关联: 服务主体 → 收发货方
├── 6. 仓储地址 (warehouse)          ← 我司仓库/客户仓库
├── 7. 联系人地址 (contact)          ← 自然人联系地址
└── 8. 银行地址 (bank)               ← 开户行地址
```

### 2.2 每类地址的归属关系

| 地址类别 | 归属对象 (owner_type) | 具体归属 (owner_id) | 说明 |
|---------|----------------------|-------------------|------|
| 注册地址 | customer / signing_entity / service_entity / settlement_entity | 对应记录 ID | 每个法律实体有一个注册地址 |
| 营业地址 | customer / entity | 对应记录 ID | 可与注册地址相同或不同 |
| 开票地址 | customer / settlement_entity | 对应记录 ID | 发票流转使用 |
| 通信地址 | customer / entity / contact | 对应记录 ID | 邮寄函件 |
| 运输地址 | service_entity → shipper_consignee | service_entity_id + shipper_consignee_id | 保留现有层级 |
| 仓储地址 | internal (我司) / customer | 仓库 ID 或客户 ID | 我司仓库或客户仓库 |
| 联系人地址 | contact | contacts.id | 自然人地址 |
| 银行地址 | settlement_entity (银行账户) | 银行账户 ID | 开户行物理地址 |

## 三、数据模型设计

### 3.1 核心思路：一套表结构，多种归属

```
核心原则:
  1. address_site 是唯一的地址主数据表
  2. 通过 owner_type + owner_id 关联任意业务对象
  3. 运输地址额外保留 shipper_consignee_id（向下兼容）
  4. 所有地址共享地址解析/用途/联系人/版本治理能力
```

### 3.4 address_usage 用途类型扩展

```diff
  现有 (7 种运输用途):
    receiving    收货地址
    shipping     发货地址
    pickup       提货地址
    delivery     送货地址
    return       退货地址
    customs      报关地址
    warehousing  仓储地址

+ 新增 (非运输用途):
+   registered   注册地址用途
+   business     营业/办公用途
+   invoice      开票用途
+   mailing      通信/邮寄用途
+   contact_addr 联系人地址用途
+   bank_addr    银行地址用途
+   headquarters 总部地址用途
+   branch       分支机构用途
+   other        其他用途
```

> **设计说明**：运输类用途（receiving/shipping 等）和非运输类用途（registered/invoice 等）共存于同一枚举。一个地址可以有多个用途标签，比如一个地址同时是 registered + mailing。

### 3.5 完整 DDL（目标态）

```sql
-- 地址主数据统一表（目标态）
CREATE TABLE address_sites (
  id                    TEXT PRIMARY KEY,
  code                  TEXT,           -- 统一编码 ADDR-YYYYMMDD-NNN
  name                  TEXT,           -- 地址名称

  -- ★ 灵活归属
  owner_type            TEXT NOT NULL,  -- customer | service_entity | signing_entity | settlement_entity | contact | internal
  owner_id              TEXT NOT NULL,  -- 归属对象 ID
  customer_id           TEXT,           -- 冗余：归属客商 ID（便于全局按客户筛选）
  address_category      TEXT NOT NULL,  -- registered | business | invoice | mailing | logistics | warehouse | contact | bank | other

  -- 运输场景保留字段（可空）
  service_entity_id     TEXT,           -- 关联服务主体（仅 logistics 类型）
  shipper_consignee_id  TEXT,           -- 关联收发货方（仅 logistics 类型）

  -- 地址结构化字段
  country               TEXT,           -- 国家/地区（默认 CN）
  province              TEXT,           -- 省（解析填充，不可手改）
  city                  TEXT,           -- 市（解析填充，不可手改）
  district              TEXT,           -- 区/县（解析填充，不可手改）
  detail_address        TEXT NOT NULL,  -- 详细地址（解析输入）
  doorplate             TEXT,           -- 门牌号（手工录入）
  postal_code           TEXT,           -- 邮政编码（手工录入）
  longitude             REAL,           -- 经度（解析填充）
  latitude              REAL,           -- 纬度（解析填充）
  geo_accuracy          TEXT DEFAULT 'unresolved', -- 解析精度

  -- 作业属性（运输/仓储场景）
  special_customs_zone  INTEGER DEFAULT 0, -- 海关特殊监管区域
  special_requirements  TEXT,           -- 特殊要求

  -- 状态与治理
  status                TEXT DEFAULT 'active', -- active | inactive
  is_default            INTEGER DEFAULT 0,     -- 是否该类别的默认地址
  is_primary            INTEGER DEFAULT 0,     -- 是否主要地址
  version               INTEGER DEFAULT 1,     -- 当前版本号
  effective_date        TEXT,           -- 生效日期
  expiry_date           TEXT,           -- 失效日期
  inactive_reason       TEXT,           -- 停用原因

  -- ★ 地址核实状态（现场纠偏机制）
  verification_status   TEXT DEFAULT 'unverified', -- unverified | verified | discrepancy_found | corrected
  verified_at           TEXT,           -- 最近核实时间
  verified_by           TEXT,           -- 核实人（客服/现场人员）
  last_correction_id    TEXT,           -- 最近一次纠偏记录 ID

  created_at            TEXT,
  updated_at            TEXT
);

-- 索引
CREATE INDEX idx_addr_owner ON address_sites(owner_type, owner_id);
CREATE INDEX idx_addr_customer ON address_sites(customer_id);
CREATE INDEX idx_addr_category ON address_sites(address_category);
CREATE INDEX idx_addr_shipper ON address_sites(shipper_consignee_id);
CREATE INDEX idx_addr_verify ON address_sites(verification_status);

-- ★ 地址纠偏记录表（现场反馈 → 源头修正）
CREATE TABLE address_corrections (
  id                    TEXT PRIMARY KEY,
  address_site_id       TEXT NOT NULL,  -- 关联地址
  reported_address      TEXT NOT NULL,  -- 现场实际地址
  reported_gps_lng      REAL,           -- 现场 GPS 经度
  reported_gps_lat      REAL,           -- 现场 GPS 纬度
  reported_by           TEXT NOT NULL,  -- 上报人（司机/仓管/客服）
  reported_by_system    TEXT,           -- 上报来源系统（TMS/WMS/COS/CIM）
  reported_at           TEXT NOT NULL,  -- 上报时间
  discrepancy_detail    TEXT,           -- 偏差描述
  photo_urls            TEXT,           -- 现场照片（JSON数组）

  status                TEXT DEFAULT 'pending', -- pending | accepted | rejected
  reviewed_by           TEXT,           -- 审核人（客服）
  reviewed_at           TEXT,           -- 审核时间
  review_comment        TEXT,           -- 审核意见
  action_taken          TEXT,           -- 处理动作：update_address | create_new | ignore
  resulting_version     INTEGER,        -- 处理后地址版本号

  created_at            TEXT,
  updated_at            TEXT
);

-- 索引
CREATE INDEX idx_corr_addr ON address_corrections(address_site_id);
CREATE INDEX idx_corr_status ON address_corrections(status);
```

## 四、菜单与页面设计

### 4.1 菜单结构

```
地址主数据                         ← 独立一级菜单（已实现 P0）
  ├── 全局地址列表                 ← /addresses（已实现，需扩展筛选维度）
  ├── 新增地址                     ← /addresses/new
  └── 地址详情/编辑                ← /addresses/[id]  /addresses/[id]/edit
```

> 地址管理以全局列表为主入口，通过筛选条件（归属类型、地址类别、用途、状态）快速定位。同时在各业务对象详情中嵌入「地址」Tab，展示该对象关联的地址列表。

### 4.2 业务对象中的地址嵌入

```
客商详情 / 主体详情 / 收发货方详情
  └── 「地址」Tab
       ├── 展示该对象下所有地址（按 address_category 分组）
       ├── "新增地址"按钮 → 跳转 /addresses/new?owner_type=xxx&owner_id=xxx
       └── 点击地址 → 跳转 /addresses/[id]
```

## 七、地址解析与门牌号拼接规范

### 7.1 解析精度边界

高德地图 Geocoding API 的解析精度上限为**道路+门牌号级别**（如"张江路 2000 号"），无法识别以下内容：

- 产业园区内部编号（"XX 半导体产业园内"）
- 楼栋/楼层/房间号（"5 号楼 301 室"）
- 仓库/月台编号（"3 号仓 B 区"）
- 企业内部建筑物名称（"研发大楼"）

### 7.2 两层地址模型

```
用户输入: "上海市浦东新区张江路2000号XX半导体产业园5号楼301室"
              │                                    │
              ▼                                    ▼
         detail_address                       doorplate
    (高德API解析，不可手改)               (人工录入，可独立修改)
              │                                    │
              └────────────┬───────────────────────┘
                           ▼
                     完整地址（下游消费）
     "上海市浦东新区张江路2000号5号楼301室"
```

### 7.3 字段职责

| 字段 | 来源 | 可否手改 | 说明 |
|------|------|---------|------|
| `detail_address` | 高德 API 解析 | ✗ 不可手改 | 道路级地址，解析结果 |
| `doorplate` | 人工录入 | ✓ 可修改 | 楼栋/楼层/房间号 |
| `province/city/district` | 高德 API 解析 | ✗ 不可手改 | 省市区 |
| `longitude/latitude` | 高德 API 解析 | ✗ 不可手改 | 经纬度坐标 |

### 7.4 变更规则

| 变更场景 | 触发动作 |
|---------|---------|
| 仅修改 `doorplate`（301→302） | 不触发重新解析，仅更新完整地址拼接，不生成版本快照 |
| 修改 `detail_address`（道路级变更） | 触发高德重新解析 → 回填省市区/经纬度 → 生成新版本快照 |
| 同时修改两者 | 先解析后拼接，生成新版本快照 |

### 7.5 下游同步

同步到 COS/TMS/WMS/DMS 的地址字段为**完整拼接地址**（detail_address + doorplate），下游系统不感知"哪部分是解析的、哪部分是手工录入的"。

```
CIM address_site:
  detail_address = "上海市浦东新区张江路2000号"
  doorplate      = "5号楼301室"

同步到 COS/TMS/WMS/DMS:
  full_address   = "上海市浦东新区张江路2000号5号楼301室"
```

## 八、地址核实与现场纠偏机制

### 8.1 业务痛点

当前存在高频场景：客户给的地址与现场实际地址不一致，但缺乏系统化反馈机制。

```
客户说地址A → 客服录A → COS传A → TMS送到A → 实际是B
→ 司机自己送到B → 系统还是A → 下次还用A → 反复出错
→ 无留痕、无反馈、无修正
```

### 8.2 核实状态流转

`address_site.verification_status` 生命周期：

```
  ┌──────────┐     首次使用     ┌──────────┐
  │ 未核实    │ ───────────────→ │ 已核实    │
  │unverified│                  │verified  │
  └────┬─────┘                  └────┬─────┘
       │                             │
       │ 现场发现偏差                 │ 后续再发现偏差
       ▼                             ▼
  ┌──────────┐     客服接受      ┌──────────┐
  │ 有偏差    │ ───────────────→ │ 已修正    │
  │discrepancy│                  │corrected │
  │_found    │                  └──────────┘
  └──────────┘
```

| 状态 | 含义 | 触发条件 |
|------|------|---------|
| `unverified` | 新建后默认状态，尚未经过现场确认 | 地址新建 |
| `verified` | 已被现场确认为准确 | 首次成功送达且无偏差 |
| `discrepancy_found` | 现场发现偏差，纠偏记录待审核 | 司机/仓管上报纠偏 |
| `corrected` | 偏差已修正，地址已更新 | 客服接受纠偏并更新地址 |

### 8.3 纠偏流程

```
  TMS司机发现偏差
       │
       ▼
  在TMS/移动端上报 ──────────────────────────────┐
  · 实际地址: "张江路1700号6号楼"                  │
  · GPS: 31.2045, 121.5837                       │
  · 备注: "实际在隔壁园区"                         │
       │                                         │
       ▼                                         │
  CIM 收到纠偏 ─────────────────────────────────  │
  · 生成 address_corrections 记录                  │
  · address_site.verification_status → discrepancy_found
  · 通知客服（待办/消息提醒）                       │
       │                                         │
       ▼                                         │
  客服核实 ─────────────────────────────────────  │
  ├─ 接受: 更新原地址 → 新版本                      │
  │   · change_summary: "现场纠偏: 张江路1688号→1700号"│
  │   · verification_status → corrected            │
  │   · 下游系统同步修正后的地址                     │
  │                                                │
  └─ 拒绝: 记录审核意见，保持原状                     │
      · verification_status → verified（如有其他证据）│
```                                                    │

### 8.4 与版本快照的协作

纠偏修正走标准版本快照流程，确保可追溯：

```
address_versions:
  v1  2026-04-01  初始创建
  v2  2026-05-15  修改联系人
  v3  2026-06-20  新增用途标签
  ★ v4  2026-06-26  现场纠偏: 详细地址 张江路1688号→张江路1700号 (来源: CORR-001, 司机刘*强上报)

address_corrections:
  CORR-001  ADDR-001  上报"张江路1700号"  pending→accepted  → v4
```

### 8.5 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 纠偏由谁审核 | CIM 客服 | 客服掌握客户关系，能判断地址真伪；司机/仓管只上报不决策 |
| 拒绝纠偏后能否再报 | 允许 | 不同司机可能在不同时间发现同一偏差 |
| 纠偏是否强制生成新版本 | 是 | 保证每次修正都有版本留痕 |
| 纠偏是否自动同步下游 | 审核通过后自动同步 | 与标准地址变更同步逻辑一致 |

  → rejected: 记录审核意见，保持原状

## 十一、关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 一张表 vs 多张表 | **一张 address_site 统一表** | 所有地址共享字段 80% 相同（省市区/经纬度/解析/版本），差异仅在归属和用途 |
| 归属模型 | **owner_type + owner_id** | 灵活关联任意业务对象，不需要为每种地址建中间表 |
| 收发货方 | **保留为独立实体** | 它有独立业务含义（USCC、联系人、类型），不只是地址的容器 |
| 运输地址层级 | **shipper_consignee_id 改为可空** | 运输地址继续关联收发货方，其他地址不填 |
| 地址用途 | **扩展 usage_type 枚举** | 一套用途体系覆盖运输+非运输场景 |
| 编码规则 | **统一 ADDR 前缀** | 简化管理，全局唯一 |
| 客户私域 | **保持不变** | owner_type + owner_id 天然隔离不同客户的地址 |
| 旧文本字段 | **迁移后保留只读** | 不破坏现有页面，逐步切换数据源 |
| 地址解析精度 | **两层模型** | 解析地址（道路级，API自动）+ 门牌号（楼栋/房间，手工录入），拼接后推送下游 |
| 现场纠偏 | **反馈闭环** | driver上报→CIM生成纠偏记录→客服审核→更新地址版本→全局同步，不留痕变有留痕 |

## 十二、owner_type 枚举与关联表映射

| owner_type | 关联表 | id 来源 | 获取名称的方式 |
|-----------|--------|---------|--------------|
| `customer` | customers | customers.id | customers.name |
| `service_entity` | service_entities | service_entities.id | service_entities.name |
| `signing_entity` | (内存 store) | signingEntity.id | signingEntity.name |
| `settlement_entity` | (内存 store) | settlementEntity.id | settlementEntity.name |
| `contact` | contacts | contacts.id | contacts.name |
| `internal` | (配置/字典) | 内部编码 | 字典名称 |

> `internal` 类型用于我司自己的地址（仓库、办公室等），不关联客户或主体表，直接通过字典维护内部组织地点。

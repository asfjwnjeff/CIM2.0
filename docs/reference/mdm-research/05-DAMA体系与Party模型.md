## 1. DAMA-DMBOK 主数据管理核心要点

### 1.1 知识体系定位

DAMA-DMBOK 定义 **11 个核心数据管理职能领域**，主数据管理（Master Data Management）是第 10 章内容。

### 1.2 主数据 vs 参考数据

| 维度 | 主数据 (Master Data) | 参考数据 (Reference Data) |
|------|---------------------|--------------------------|
| 数据来源 | 生产系统（HR、ERP、CRM） | 外部标准或内部配置 |
| 变更频率 | 中低频（如客户地址更新） | 低频（如国家代码增减） |
| 管理重点 | 实体解析与唯一性 | 代码一致性维护 |
| 典型示例 | 客户、供应商、产品、组织 | 国家代码、币种、性别、行业分类 |

### 1.3 客户主数据的边界

**纳入范围**（以商业银行为例）：
- 个人客户：客户统一编号、姓名、证件、国籍/民族/性别、地址/联系电话、职业/收入等级
- 对公客户：客户名称、客户类型、法人代表证件号码、所属行业、注册资本、统一社会信用代码

**边界界定三原则**：
1. **"一数一源一标准"** — 每个客户主数据属性只能有一个权威源头系统
2. **唯一性识别** — 通过姓名/手机号/证件号组合判定客户唯一性，建立"黄金记录"
3. **跨系统共享** — 销售、客服、财务系统共享同一份客户主数据正本

### 1.4 主数据管理的四大体系

| 体系 | 内容 |
|------|------|
| 标准体系 | 数据编码规则、属性规范 |
| 管控体系 | 组织、流程、评估与考核、系统 |
| 质量体系 | 合理性、真实性、完整性、唯一性、及时性 |
| 安全体系 | 分级、授权 |

## 2. Party（参与方）模型

### 2.1 什么是 Party 模型

Party（参与方）是 MDM 领域的核心抽象概念，表示能够与企业建立业务关系的任何实体。

```
                    Party（参与方）—— 超类型
                    - 全局唯一标识
                    - 名称 / 地址 / 联系方式（共享属性）
                    - 隐私偏好
                    - 状态 / 生命周期
                 /          |          \
         Organization     Person      Group
         (组织/企业)     (个人)       (群组)
              |
         Legal Entity
         (法律实体)
         - LEI / DUNS / 税号
         - 法律形式
         - 注册资本
```

### 2.2 核心子对象

| 子对象 | 说明 |
|--------|------|
| Names | 名称集合（中文名、英文名、简称、曾用名） |
| Addresses | 地址集合（注册地址、营业地址、通信地址） |
| Contact Methods | 联系方式（电话、邮箱、微信等） |
| Privacy Preferences | 隐私偏好（GDPR 等合规） |
| Sites | 物理场所（工厂、仓库、门店） |
| Roles | 角色（Customer、Supplier、Partner 等） |

### 2.3 Party 模型 vs 独立实体模型

| | Party 模型 | 独立实体模型 |
|---|---|---|
| 设计思路 | 一个 Party 可扮演多角色 | 每个角色创建独立实体 |
| 数据冗余 | 低（共享属性只存一份） | 高（同公司多条记录） |
| 360 视图 | 天然支持 | 需要关联映射 |
| 治理复杂度 | 需处理多态性 | 相对简单 |
| 代表方案 | SAP BP、金蝶 AMDM | 用友 MDM、中远海运 |

## 3. 层级建模的两种方式

### 方式一：固定层级（设计时定义）

适合层级数**预先已知**的场景，各级别间通过外键关联。

### 方式二：N 级自引用层级（运行时灵活）

- 使用单一实体 + **自引用外键**（parentFk 指向自身）
- 根节点 parentFk 为 optional/null
- 支持：未知深度层级、不规则层级、多套并行层级

**推荐**：除非层级数严格固定，否则使用自引用模式以保留运行时灵活性。

### CIM2.0 适用场景

```
法律实体 A（母公司）
├── 法律实体 B（子公司，服务主体）
└── 法律实体 C（子公司，签约主体 + 服务主体）
    ├── 收发货方 1
    │   ├── 地址站点 ①
    │   └── 地址站点 ②
    └── 收发货方 2
```

上图中的**法律实体层级**（母公司-子公司）适合用自引用模式，**业务层级**（法律实体→收发货方→地址站点）适合用固定层级。

## 4. MDM 常见反模式与避坑指南

### 4.1 技术层面反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 为每个角色建独立表 | 数据冗余、无法统一视图 | Party 超类型 + 角色关联表 |
| JSON 字段过度使用 | 无法索引、查询困难、数据校验弱 | 核心属性用结构化字段，保留少量 JSON 用于扩展 |
| 忽略编码的全局唯一性 | 系统对接时 ID 冲突 | 采用全局唯一标识（UUID 或统一编码规则） |
| "先建后治" | 脏数据迁移后从第一天就破坏系统信任 | 数据清洗必须在迁移前完成 |

### 4.2 组织层面反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 没有明确的 Data Owner | 同一属性多人可改、数据失控 | 每个主数据域必须有明确的 Data Owner |
| 纯集中式管控 | 大型分散组织中基层反弹 | 联邦式部署：中央定标准，本地可自治 |
| 主数据标准化力度被低估 | 编码长度不一致、格式差异、语言/货币本地化等问题 | 标准化应从最初的建模就开始 |

### 4.3 实施经验教训

1. **利益相关方持续对齐**：某财富 500 强案例中，利益相关方在早期阶段偏离原始需求，导致治理失灵
2. **数据清洗先行**：脏数据迁移至 MDM 后，会从第一天就破坏系统信任
3. **联邦式优于纯集中式**：大型组织中，纯集中模式可能失败
4. **不要低估标准化难度**：编码长度、ID 格式、语言/货币本地化等问题常被低估

## 5. 对 CIM2.0 的启示

1. **CIM 的当前模型已接近 Party 模型雏形**：一个客户记录上有 `entityTypes` 数组（签约/服务/结算），这本质上就是 Party 的角色标签
2. **建议从 JSON 字段逐步迁移到结构化表**：当前 CIM 使用大量 JSON 字段存储子对象。在平台化升级时，核心属性应建独立表
3. **层级关系建议用自引用模式**：法律实体之间的母子公司关系使用自引用 parentFk
4. **必须有明确的 Data Owner 机制**：每个主数据属性有且只有一个维护入口
